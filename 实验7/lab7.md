### 2. 关键数据结构

*   **`struct superblock`**：定义文件系统布局，位于磁盘第 1 块。
*   **`struct inode`**：内存中的文件元数据副本，包含 `ref`（引用计数）、`valid`（是否已读入）、`addrs`（数据块索引）。
*   **`struct log`**：日志系统控制块，维护 `outstanding`（活跃事务数）和日志头缓冲区。

### 3. 核心流程：带日志的写操作

为了保证崩溃一致性，写操作被包裹在事务中：

```c
begin_op();             // 1. 开启事务，检查日志空间
ilock(ip);              // 2. 锁定 Inode
writei(ip, ...);        // 3. 写入数据（实际调用 log_write 写入缓存，标记为脏）
iunlock(ip);            // 4. 解锁 Inode
end_op();               // 5. 结束事务，触发 commit（写入磁盘日志区 -> 写入磁盘数据区）
```

## 三、实现细节

### 关键函数1：日志提交 (`log.c/commit`)

```c
void commit() {
    if (log.lh.n > 0) {
        write_log();      // A. 将脏块写入磁盘上的日志区域
        write_head();     // B. 更新磁盘上的日志头 (Commit Point!)
        install_trans();  // C. 将日志区的数据拷贝到文件系统实际位置
        log.lh.n = 0; 
        write_head();     // D. 清空日志头
    }
}
```
**技术要点**：步骤 B 是原子性的关键。在 B 完成前断电，重启后系统会忽略日志；在 B 完成后断电，重启后系统会重做 C 步骤，保证数据不丢失。

### 难点突破

1.  **日志系统的死锁预防**：
    *   **问题**：如果一个事务修改的块数超过了日志区大小，或者并发事务总块数过多，会导致日志系统无法提交，进而死锁（等待空闲空间的进程持有锁，而提交进程无法获得锁）。
    *   **解决**：限制 `MAXOPBLOCKS`（单次操作最大块数），并在 `begin_op` 中检查剩余日志空间。如果空间不足，进程进入睡眠，等待当前事务组提交释放空间。

2.  **块缓存的并发与性能**：
    *   **问题**：多进程同时读写同一个块时，如何保证数据一致性且不严重影响性能？
    *   **解决**：采用了两级锁机制。`bcache.lock`（自旋锁）保护缓存链表结构，`b->lock`（睡眠锁）保护具体缓冲区的数据。查找缓存时持有全局锁，找到后释放全局锁并获取块锁，最大限度减小临界区。

### 手册思考题简答：

#### 1. 设计权衡

*   **xv6简单文件系统的优缺点？**
    **优点**：代码结构清晰，实现简单，具备基本的崩溃恢复能力。**缺点**：性能较低（同步写日志），大文件支持有限，线性目录查找慢。
*   **简单性与性能的平衡？**
    xv6 选择了简单性。现代文件系统通过日志校验和、延迟分配、由范围（Extent）管理块等复杂技术来提升性能。

#### 2. 一致性保证

*   **日志系统如何确保原子性？**
    依靠**日志头**的原子写入。如果日志头显示 `n > 0`，则认为事务已提交；否则视为未提交。
*   **恢复过程中再次崩溃？**
    日志恢复操作是**幂等**的。即无论执行多少次 `install_trans`（将日志块复制到数据块），结果都是一样的。所以再次崩溃后重启只需再次运行恢复过程即可。

#### 3. 性能优化

*   **性能瓶颈？**
    **同步写日志**。每次 `commit` 都必须等待磁盘 I/O 完成，阻塞了进程。
    **目录查找**。线性扫描导致大量 `bread` 操作。
*   **如何改进目录查找？**
    使用**目录项缓存**或在磁盘上使用 B-Tree 组织目录项。

#### 4. 可扩展性

*   **如何支持更大的文件？**
    引入**多级间接块**（如三级间接块）或**Extent**（由起始块号+长度组成）来描述连续的数据块。
*   **现代特性？**
    快照、写时复制、在线扩容、重复数据删除等。

#### 5. 可靠性

*   **如何检测损坏？**
    使用 `fsck`（文件系统检查工具）在离线状态下扫描 inode 引用计数和位图一致性。
*   **在线检查？**
    现代文件系统在元数据中加入 **Checksum（校验和）**，读取时即时校验，发现错误时自动切换到只读模式或尝试修复

## 五、问题与总结

### 遇到的问题

#### 问题1：并发测试中 Panic "bget: no buffers"
**现象**：在并发测试中，系统偶尔崩溃，提示缓冲区耗尽。
**原因分析**：`NBUF` 设置过小（例如 10），而 `MAXOPBLOCKS` 为 10。当多个进程并发进行文件操作（如 `write`）时，它们可能各自持有了部分缓冲区但都在等待更多缓冲区，且都无法提交事务（因为提交需要更多缓冲区来读写日志头），导致死锁或资源耗尽。
**解决方法**：调整 `NBUF` 大小为 `MAXOPBLOCKS * 3` 以上，确保即使在高负载下也有足够的缓冲区供日志提交使用。

#### 问题2：文件链接数错误
**现象**：删除文件后，inode 未被回收（位图显示仍被占用）。
**原因**：在 `sys_link` 实现中，增加了 `nlink` 但在错误处理路径（如目标目录不存在）中忘记了减少 `nlink`。
**解决方法**：在 `sys_link` 的错误处理 `goto bad` 标签后，添加了回滚 `nlink` 的代码。

### 实验收获

1.  **崩溃一致性的奥义**：理解了为什么简单的“写数据”操作在文件系统中如此复杂。WAL 机制虽然牺牲了部分写入性能（写两次），但换来了极其宝贵的可靠性。没有日志的文件系统在断电面前是极其脆弱的。
2.  **缓存不仅仅是加速**：Buffer Cache 既是性能加速器，也是数据同步点。所有的磁盘操作都必须经过它，这使得它成为了实现原子性和顺序性的关键枢纽。
3.  **分层设计的力量**：文件系统是操作系统中最复杂的子系统之一。通过将 inode、dir、log、buf 分层实现，每层只关注自己的逻辑，极大地降低了系统复杂度。

### 改进方向
1.  **支持大文件**：目前仅支持一级间接块，最大文件限制在 268KB 左右。可以实现二级间接块以支持 MB/GB 级文件。
2.  **目录索引优化**：目前的目录项查找是线性扫描 ($O(N)$)。可以引入 B+ 树或哈希表来优化目录查找性能。
