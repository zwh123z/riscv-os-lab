## 二、技术设计

### 1. 系统架构设计

我的启动流程设计如下，旨在以最简方式进入C语言环境：

```mermaid
graph LR
A[QEMU Power On] --> B[跳转至 0x80000000]
B --> C[entry.S: 设置栈指针 SP]
C --> D[main.c: 内核入口]
D --> E[UART Driver: 内存映射IO]
E --> F[Output: Hello OS]
```

**与xv6的对比**：
*   **多核处理**：xv6在 `start.c` 中会读取 `mhartid` 来区分不同的CPU核心，让非0号核心自旋等待。本实验为了简化，假定单核运行，直接执行初始化。
*   **模式切换**：xv6在启动阶段涉及从Machine Mode到Supervisor Mode的切换。本实验暂未处理特权级切换，主要关注裸机环境搭建。

### 2. 内存布局设计

根据RISC-V QEMU virt机器的规范，内存布局设计如下：

| 地址范围     | 用途       | 说明                            |
| :----------- | :--------- | :------------------------------ |
| `0x10000000` | UART0      | 串口寄存器基地址 (MMIO)         |
| `0x80000000` | .text      | 内核代码段起始位置 (QEMU跳转点) |
| `0x8000xxxx` | .data/.bss | 数据段                          |
| `end` ~      | Stack      | 内核栈 (向下生长)               |

**设计理由**：QEMU默认将内核加载到 `0x80000000`，因此链接脚本必须以此为基址，否则指令跳转和数据访问会出错。

### 3. 核心流程：栈的初始化

在跳转到C语言 `main` 函数之前，必须设置栈指针（sp）。

```assembly
    .section .text
    .global _start
_start:
    # 1. 设置栈指针
    la sp, stack_top
    
    # 2. 跳转到C代码
    call main
    
    # 3. 防止main返回后跑飞
    wfi
```

**设计选择**：我选择在 `.bss` 段后预留4KB空间作为栈，并在链接脚本中定义 `stack_top` 符号。这比硬编码绝对地址更灵活，随内核大小自动调整。

## 三、实现细节

### 关键代码1：链接脚本 (kernel.ld)

```ld
OUTPUT_ARCH( "riscv" )
ENTRY( _start )

SECTIONS
{
  . = 0x80000000; /* QEMU加载基址 */

  .text : {
    *(.text .text.*)
  }

  /* ... data和bss段省略 ... */

  /* 定义栈空间 */
  . = ALIGN(16);
  . += 4096;      /* 4KB 栈大小 */
  stack_top = .;  /* 定义栈顶符号供汇编使用 */
}
```

**源码理解**：
*   `ENTRY(_start)`：告诉链接器程序的入口是 `_start` 符号，而不是默认的 `_start` (如果未定义) 或文件开头。
*   `stack_top = .`：`.` 代表当前地址计数器。栈是向下生长的（高地址 -> 低地址），所以栈顶指针应指向保留空间的末尾。

### 关键代码2：UART驱动 (uart.c)

```c
#define UART0 0x10000000L
#define THR 0 // Transmit Holding Register

void uart_putc(char c) {
    // 强制类型转换为 volatile 指针，防止编译器优化内存读写
    volatile unsigned char *uart = (unsigned char *)UART0;
    
    // 直接写入寄存器
    // 注：简化实现，未检查LSR寄存器的发送缓冲区状态
    uart[THR] = c;
}
```

### **难点突破**：

*   **MMIO的理解**：起初不理解为什么可以直接向 `0x10000000` 写数据。通过查阅文档明白RISC-V采用内存映射IO，该地址对应硬件寄存器而非RAM。
*   **`volatile` 关键字**：如果不加 `volatile`，编译器可能认为向同一个内存地址（UART0）写入数据是无效的（因为没有读取），从而优化掉写操作，导致无法输出。

### **手册思考题简答**：

#### 1. 启动栈的设计
*   **如何确定大小？**
    根据内核启动时的**最大函数调用深度**和**局部变量/上下文保存**的需求估算，通常分配 4KB（一页）即可。
*   **太小后果及检测？**
    **后果**：栈溢出，覆盖低地址的全局变量或代码，导致系统崩溃或逻辑错误。
    **检测**：在栈底写入特定魔数，运行时检查是否被修改；或利用页表设置保护页触发异常。

#### 2. BSS段清零
*   **不清零的后果？**
    未初始化的全局变量将包含随机垃圾值而非 0，导致类似 `if(flag == 0)` 的逻辑判断失效，程序行为不可预测。
*   **何时可省略？**
    当引导加载程序已经替内核完成了清零工作时。

#### 3. 与xv6的对比
*   **简化了什么？**
    去除了多核启动协调（让非主核空转）和特权级切换（M模式转S模式）的代码，默认单核直接运行。
*   **潜在问题？**
    若在多核环境下运行会引发竞争崩溃；若未切换至 S 模式，将无法使用分页机制和内存保护。

#### 4. 错误处理
*   **UART失败怎么处理？**
    系统无法输出，通常让 CPU 进入死循环以冻结现场。
*   **最小错误显示机制？**
    **GDB调试**（查看死循环位置）或向约定好的**物理内存地址写入特定错误码**。

## 五、问题与总结

### 遇到的问题

#### 问题1：输出乱码或无输出

**现象**：程序运行后QEMU卡住，无任何字符显示。
**原因分析**：
1. 链接脚本中地址设置错误，导致代码加载位置与QEMU跳转位置不符。
2. `main` 函数返回后，CPU继续执行内存中后续的垃圾指令。
**解决方法**：
1. 修正 `kernel.ld` 中的基址为 `0x80000000`。
2. 在 `entry.S` 调用 `main` 后添加死循环 `loop: j loop` 或 `wfi` 指令。

#### 问题2：编译报错 "relocation truncated to fit"

**现象**：在引用全局变量时链接器报错。
**原因分析**：使用了 `cmodel=medlow` (默认)，但访问的地址范围超出了该模型的限制，或者链接脚本段定义顺序有误。
**解决方法**：虽然本实验代码量小未触发严重问题，但在 `CFLAGS` 中添加 `-mcmodel=medany` 是更稳妥的做法，允许代码在任意地址运行。

### 实验收获

1.  **脱离标准库编程**：第一次体验了没有 `stdio.h` 的编程，理解了 `printf` 底层最终是如何通过向特定内存地址写数据来控制硬件的。
2.  **链接脚本的作用**：理解了代码不仅仅是编译出来的，还需要被“放置”在正确的内存位置才能运行。链接脚本就是这个“放置”规则的说明书。

### 改进方向

1.  **完善UART驱动**：当前实现是“盲写”，没有检查发送缓冲区是否为空（LSR寄存器）。如果在高速发送大量数据时可能会丢包。应增加状态位检查。
2.  **支持printf**：目前只能输出字符或裸字符串，下一步可以实现一个简单的格式化输出函数，方便后续实验调试。
